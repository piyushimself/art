PART 1: BASIC PROJECTS (1-20)

1 Hello World

Concept: Contract structure, public functions

Every Solidity file starts with a licence and a pragma. A contract is like a class: it bundles state and functions. This one has no state at all, so it is marked pure.

// SPDX-License-Identifier: MIT
pragma solidity ^0.8.20;

contract HelloWorld {
    function greet() public pure returns (string memory) {
        return "Hello, World!";
    }
}

Key Takeaways

  • public makes the function callable from outside and inside the contract.
  • pure promises the function neither reads nor writes blockchain state.
  • Strings need an explicit data location (memory) when returned.

Security Note

Deployed bytecode is immutable. Even a trivial contract deserves a test on a local chain before it goes anywhere public.

2 Simple Storage

Concept: State variables, getters, setters

State variables live in the contract's permanent storage. A setter writes to storage (costs gas); a getter marked view only reads (free when called off-chain).

// SPDX-License-Identifier: MIT
pragma solidity ^0.8.20;

contract SimpleStorage {
    uint256 private number;

    function set(uint256 _n) external {
        number = _n;
    }

    function get() external view returns (uint256) {
        return number;
    }
}

Key Takeaways

  • uint256 is the default unsigned integer; it holds 0 until written.
  • external is slightly cheaper than public for functions only called from outside.
  • Declaring a variable public auto-generates a getter for you.

Security Note

private does not mean secret. Anyone can read raw storage slots from a node, so never keep passwords or secrets on-chain.

3 Counter

Concept: Arithmetic operations

Since Solidity 0.8 arithmetic is checked: overflow and underflow revert automatically. An explicit require gives callers a readable error message.

// SPDX-License-Identifier: MIT
pragma solidity ^0.8.20;

contract Counter {
    uint256 public count;

    function increment() external {
        count += 1;
    }

    function decrement() external {
        require(count > 0, "Counter: already zero");
        count -= 1;
    }
}

Key Takeaways

  • += and -= are checked operations in 0.8+.
  • require(cond, msg) reverts the whole transaction if cond is false.
  • Reverted transactions undo all state changes but still cost the gas used.

Security Note

Anyone can call these functions. If a counter drives business logic, add access control (Project 5) before shipping.

4 Boolean Flag

Concept: Boolean operations

Booleans are the simplest building block of switches, pause states and permission checks. Negation with ! flips the value.

// SPDX-License-Identifier: MIT
pragma solidity ^0.8.20;

contract BooleanFlag {
    bool public flag;

    function toggle() external {
        flag = !flag;
    }

    function set(bool value) external {
        flag = value;
    }

    function both(bool a, bool b) external pure returns (bool) {
        return a && b;             // also: ||  and  !
    }
}

Key Takeaways

  • Default value of a bool is false.
  • Logical operators: &&, ||, ! - they short-circuit.
  • One bool still occupies a storage slot unless packed with neighbours.

Security Note

A flag anyone can flip is a vulnerability if it guards anything important. Restrict who may toggle it.

5 Owner-only Function

Concept: Access control

The constructor runs once at deployment, so msg.sender there is the deployer. Storing it as owner lets later functions verify the caller.

// SPDX-License-Identifier: MIT
pragma solidity ^0.8.20;

contract OwnerOnly {
    address public owner;
    uint256 public secret;

    constructor() {
        owner = msg.sender;
    }

    function setSecret(uint256 v) external {
        require(msg.sender == owner, "not owner");
        secret = v;
    }
}

Key Takeaways

  • msg.sender is the immediate caller of the current function.
  • The constructor executes only during deployment.
  • Make owner immutable when it never changes: cheaper reads.

Security Note

Never authorise with tx.origin. A malicious contract called by the owner would pass that check (a classic phishing bug).

6 Mapping Basics

Concept: Mappings

A mapping is a hash table whose every possible key already exists with the default value 0. It is the workhorse for per-user data.

// SPDX-License-Identifier: MIT
pragma solidity ^0.8.20;

contract MappingBasics {
    mapping(address => uint256) public balances;

    function credit(uint256 amount) external {
        balances[msg.sender] += amount;
    }

    function debit(uint256 amount) external {
        require(balances[msg.sender] >= amount, "insufficient");
        balances[msg.sender] -= amount;
    }
}

Key Takeaways

  • Missing keys return 0, there is no 'key not found'.
  • Mappings cannot be iterated or have their length read.
  • The value is keyed by keccak256(key . slot) internally.

Security Note

This toy lets anyone credit themselves. Real balances must change only through checked deposits or transfers.

7 Array Operations

Concept: Arrays and loops

Dynamic arrays can grow with push and shrink with pop. To delete from the middle cheaply, overwrite the slot with the last element and pop (swap-and-pop).

// SPDX-License-Identifier: MIT
pragma solidity ^0.8.20;

contract ArrayOps {
    uint256[] public items;

    function append(uint256 v) external { items.push(v); }

    function update(uint256 i, uint256 v) external {
        require(i < items.length, "out of range");
        items[i] = v;
    }

    // swap-and-pop: O(1), order is not preserved
    function remove(uint256 i) external {
        require(i < items.length, "out of range");
        items[i] = items[items.length - 1];
        items.pop();
    }

    function sum() external view returns (uint256 total) {
        for (uint256 i = 0; i < items.length; i++) total += items[i];
    }
}

Key Takeaways

  • delete items[i] only zeroes the slot, it leaves a hole.
  • Looping over storage arrays costs gas per element.
  • Out-of-range access reverts automatically, an explicit require is friendlier.

Security Note

Unbounded loops over user-growable arrays can exceed the block gas limit and permanently brick a function (DoS). Prefer pull patterns or pagination.

8 Structs and Nested Mappings

Concept: Structs, nested mappings

Structs group related fields into one type. Nested mappings model relationships such as 'who follows whom' without any loops.

// SPDX-License-Identifier: MIT
pragma solidity ^0.8.20;

contract Profiles {
    struct Profile {
        string name;
        uint8 age;
        bool active;
    }

    mapping(address => Profile) public profiles;
    mapping(address => mapping(address => bool)) public follows;

    function setProfile(string calldata name, uint8 age) external {
        profiles[msg.sender] = Profile(name, age, true);
    }

    function follow(address who) external {
        require(profiles[who].active, "no such profile");
        follows[msg.sender][who] = true;
    }
}

Key Takeaways

  • Struct fields are packed into slots in declaration order.
  • mapping(a => mapping(b => c)) is a two-key lookup table.
  • Use calldata for external function arguments you only read.

Security Note

Storing personal data on a public chain is permanent. Treat every field as world-readable forever.

9 Enums

Concept: Enum basics

An enum names a fixed set of states. Combined with a modifier, it becomes a tiny state machine where only legal transitions are possible.

// SPDX-License-Identifier: MIT
pragma solidity ^0.8.20;

contract Lifecycle {
    enum State { Created, Locked, Released, Cancelled }
    State public state;              // defaults to Created

    modifier inState(State s) {
        require(state == s, "wrong state");
        _;
    }

    function lock() external inState(State.Created) {
        state = State.Locked;
    }

    function release() external inState(State.Locked) {
        state = State.Released;
    }

    function cancel() external {
        require(state == State.Created || state == State.Locked, "too late");
        state = State.Cancelled;
    }
}

Key Takeaways

  • Enums are stored as small integers starting from 0.
  • Model transitions explicitly; forbid everything else.
  • The _; in a modifier marks where the function body runs.

Security Note

State machines without access control let anyone drive the transitions. Add ownership checks (Project 12) for real use.

10 Ether Transfer

Concept: payable functions

A function marked payable can receive ETH. Withdrawals should update internal accounting first and only then send ETH: the checks-effects-interactions order.

// SPDX-License-Identifier: MIT
pragma solidity ^0.8.20;

contract EtherVault {
    mapping(address => uint256) public balances;

    function deposit() external payable {
        balances[msg.sender] += msg.value;
    }

    function withdraw(uint256 amount) external {
        require(balances[msg.sender] >= amount, "insufficient");
        balances[msg.sender] -= amount;               // effects first
        (bool ok, ) = msg.sender.call{value: amount}(""); // interaction last
        require(ok, "transfer failed");
    }
}

Key Takeaways

  • msg.value is the ETH (in wei) sent with the call.
  • Prefer call{value: x} over transfer/send; check the return flag.
  • 1 ether = 1018 wei.

Security Note

Sending ETH hands control to the recipient. If you update balances after the call, the recipient can re-enter (see Project 32).

11 Gas Tracking

Concept: Gas optimization

Storage writes (SSTORE) dominate gas cost. Caching a storage value in memory, doing the arithmetic there and writing back once is a standard optimisation. gasleft() lets you measure the difference.

// SPDX-License-Identifier: MIT
pragma solidity ^0.8.20;

contract GasLab {
    uint256 public total;
    event GasUsed(string label, uint256 gas);

    function costly(uint256 n) external {
        uint256 g = gasleft();
        for (uint256 i = 0; i < n; i++) { total += i; }  // SSTORE each loop
        emit GasUsed("costly", g - gasleft());
    }

    function cheaper(uint256 n) external {
        uint256 g = gasleft();
        uint256 t = total;                               // cache once
        for (uint256 i = 0; i < n; ) { t += i; unchecked { ++i; } }
        total = t;                                       // single SSTORE
        emit GasUsed("cheaper", g - gasleft());
    }
}

Key Takeaways

  • Read storage once, compute in memory, write back once.
  • unchecked skips overflow checks: use only when overflow is impossible.
  • Run both functions in Remix and compare the emitted numbers.

Security Note

Do not trade safety for tiny savings. Unchecked math is a common source of audit findings.

12 Modifier Basics

Concept: Function modifiers

Modifiers wrap a function with reusable checks. Several can be stacked and they execute left to right.

// SPDX-License-Identifier: MIT
pragma solidity ^0.8.20;

contract Modifiers {
    address public owner = msg.sender;
    bool public paused;
    uint256 public value;

    modifier onlyOwner() {
        require(msg.sender == owner, "not owner");
        _;
    }
    modifier whenNotPaused() {
        require(!paused, "paused");
        _;
    }
    modifier validAmount(uint256 a) {
        require(a > 0 && a <= 1_000, "bad amount");
        _;
    }

    function setPaused(bool p) external onlyOwner { paused = p; }

    function setValue(uint256 v) external whenNotPaused validAmount(v) {
        value = v;
    }
}

Key Takeaways

  • Modifiers can take arguments, as in validAmount(v).
  • Code after _; runs after the body, handy for post-conditions.
  • Keep modifiers small: heavy logic hides inside them.

Security Note

A pause switch is only useful if the owner key is safe. Consider a multisig (Project 34) as owner.

13 Timestamp Validation

Concept: block.timestamp

block.timestamp is the current block's time in seconds. Use it for deadlines measured in minutes or longer, never for exact ordering.

// SPDX-License-Identifier: MIT
pragma solidity ^0.8.20;

contract TimeGate {
    uint256 public immutable deadline;
    uint256 public joined;

    constructor(uint256 duration) {
        deadline = block.timestamp + duration;
    }

    modifier beforeDeadline() { require(block.timestamp < deadline, "closed"); _; }
    modifier afterDeadline()  { require(block.timestamp >= deadline, "still open"); _; }

    function join() external beforeDeadline { joined++; }

    function timeLeft() external view returns (uint256) {
        return block.timestamp >= deadline ? 0 : deadline - block.timestamp;
    }

    function finalize() external view afterDeadline returns (uint256) {
        return joined;
    }
}

Key Takeaways

  • Time units: 1 minutes, 1 hours, 1 days are built in.
  • immutable values are set once in the constructor and cost no storage read.
  • Use >= and < consistently to avoid off-by-one gaps.

Security Note

Block producers can nudge the timestamp by a few seconds. Never let a contract's fairness depend on second-level precision.

14 Event Emission

Concept: Events and logging

Events write cheap, searchable logs. Front ends and indexers subscribe to them instead of polling storage. Up to three parameters can be indexed for filtering.

// SPDX-License-Identifier: MIT
pragma solidity ^0.8.20;

contract EventDemo {
    uint256 public value;

    event ValueChanged(
        address indexed by,
        uint256 oldValue,
        uint256 newValue
    );

    function set(uint256 v) external {
        uint256 old = value;
        value = v;
        emit ValueChanged(msg.sender, old, v);
    }
}

Key Takeaways

  • indexed parameters become filterable topics.
  • Logs are far cheaper than storage but unreadable by contracts.
  • Emit an event for every important state change.

Security Note

Off-chain monitoring of events is your alarm system: unexpected ownership or pause events are often the first sign of compromise.

15 Fallback Function

Concept: fallback and receive functions

receive() handles plain ETH transfers with empty calldata. fallback() handles calls to functions that do not exist. Having both lets you tell the two cases apart.

// SPDX-License-Identifier: MIT
pragma solidity ^0.8.20;

contract FallbackDemo {
    event Received(address indexed from, uint256 amount);
    event FallbackCalled(address indexed from, uint256 amount, bytes data);
    uint256 public totalReceived;

    // empty calldata + ETH
    receive() external payable {
        totalReceived += msg.value;
        emit Received(msg.sender, msg.value);
    }

    // unknown selector (payable is optional)
    fallback() external payable {
        totalReceived += msg.value;
        emit FallbackCalled(msg.sender, msg.value, msg.data);
    }
}

Key Takeaways

  • Without receive(), plain ETH transfers to the contract revert.
  • msg.data in fallback holds the raw calldata.
  • Proxies (Project 30) rely on fallback to forward every call.

Security Note

Keep receive() tiny. With the 2300-gas stipend used by transfer/send, any storage write would fail.

16 Token Tracker

Concept: Balances and mappings

Mappings are great for lookups but cannot be listed. Keep a parallel array of holders (added once) if you need to enumerate them.

// SPDX-License-Identifier: MIT
pragma solidity ^0.8.20;

contract TokenTracker {
    mapping(address => uint256) public balanceOf;
    address[] public holders;
    mapping(address => bool) private isHolder;

    constructor(uint256 supply) {
        _credit(msg.sender, supply);
    }

    function transfer(address to, uint256 amount) external {
        require(balanceOf[msg.sender] >= amount, "insufficient");
        balanceOf[msg.sender] -= amount;
        _credit(to, amount);
    }

    function _credit(address to, uint256 amount) private {
        if (!isHolder[to]) { isHolder[to] = true; holders.push(to); }
        balanceOf[to] += amount;
    }

    function holderCount() external view returns (uint256) {
        return holders.length;
    }
}

Key Takeaways

  • A bool mapping avoids pushing the same address twice.
  • private functions are only callable from inside this contract.
  • This is the skeleton of ERC20 (Project 21).

Security Note

Do not loop over holders in a transaction: an attacker can grow it until the loop cannot fit in a block.

17 Multiplier Contract

Concept: require statement and validation

Validate inputs at the boundary. Here we reject zero and oversized values before doing arithmetic and storing the result.

// SPDX-License-Identifier: MIT
pragma solidity ^0.8.20;

contract Multiplier {
    uint256 public constant FACTOR = 7;
    uint256 public constant MAX_INPUT = type(uint128).max;
    uint256 public lastResult;

    function multiply(uint256 x) external returns (uint256) {
        require(x > 0, "zero input");
        require(x <= MAX_INPUT, "input too large");
        lastResult = x * FACTOR;
        return lastResult;
    }
}

Key Takeaways

  • constant values are inlined at compile time.
  • type(uint128).max gives the largest value of a type.
  • Fail early: cheap checks first, storage writes last.

Security Note

0.8 reverts on overflow, but inside unchecked { } blocks it wraps silently. Bound your inputs anyway.

18 Random Number Generator

Concept: Hashing and randomness

keccak256 turns any input into a 256-bit hash. Hashing block data plus a nonce looks random but is fully predictable, so this is a teaching example only.

// SPDX-License-Identifier: MIT
pragma solidity ^0.8.20;

contract PseudoRandom {
    uint256 private nonce;

    // FOR LEARNING ONLY - predictable, never use for real value
    function roll(uint256 max) external returns (uint256) {
        require(max > 0, "max is zero");
        nonce++;
        bytes32 h = keccak256(
            abi.encodePacked(block.prevrandao, block.timestamp, msg.sender, nonce)
        );
        return uint256(h) % max;
    }
}

Key Takeaways

  • abi.encodePacked concatenates values before hashing.
  • block.prevrandao replaced block.difficulty after the Merge.
  • Modulo by a non-power-of-two introduces slight bias.

Security Note

On-chain 'randomness' can be simulated by an attacker contract in the same transaction. Use Chainlink VRF or commit-reveal for anything valuable.

19 Basic Voting

Concept: Basic logic and mapping

A minimal ballot: each address may vote once for a candidate id, and a view function scans for the current leader.

// SPDX-License-Identifier: MIT
pragma solidity ^0.8.20;

contract BasicVoting {
    uint256 public immutable candidateCount;
    mapping(uint256 => uint256) public votes;
    mapping(address => bool) public hasVoted;

    constructor(uint256 _count) {
        require(_count > 1, "need 2+ candidates");
        candidateCount = _count;
    }

    function vote(uint256 id) external {
        require(id < candidateCount, "no such candidate");
        require(!hasVoted[msg.sender], "already voted");
        hasVoted[msg.sender] = true;
        votes[id]++;
    }

    function leader() external view returns (uint256 best) {
        for (uint256 i = 1; i < candidateCount; i++) {
            if (votes[i] > votes[best]) best = i;
        }
    }
}

Key Takeaways

  • Mark hasVoted before doing anything else to block double votes.
  • view functions can loop freely because they cost no gas off-chain.
  • Ties resolve to the lowest id in this design.

Security Note

One address one vote is trivially bypassed with many addresses (Sybil attack). Real systems weight votes by tokens or verified identity.

20 String Operations

Concept: Working with strings

Solidity strings are byte arrays without helper methods. Use string.concat to join, bytes(s).length for size and hash comparison for equality.

// SPDX-License-Identifier: MIT
pragma solidity ^0.8.20;

contract StringOps {
    string public text;

    function set(string calldata s) external {
        text = s;
    }

    function append(string calldata s) external {
        text = string.concat(text, s);
    }

    function length() external view returns (uint256) {
        return bytes(text).length;          // bytes, not characters
    }

    function equals(string calldata s) external view returns (bool) {
        return keccak256(bytes(text)) == keccak256(bytes(s));
    }
}

Key Takeaways

  • == is not defined for strings; compare hashes.
  • Length counts UTF-8 bytes: an emoji is 4.
  • Prefer bytes32 for short fixed labels, it is much cheaper.

Security Note

Long user strings in storage are expensive and can be used to bloat state. Cap the length you accept.

21 ERC20 Token

Concept: Token standards

ERC20 is the fungible token interface: balances, transfers and delegated spending through allowances. Inherit from OpenZeppelin instead of hand-rolling it.

// SPDX-License-Identifier: MIT
pragma solidity ^0.8.20;

import "@openzeppelin/contracts/token/ERC20/ERC20.sol";

contract MyToken is ERC20 {
    constructor(uint256 initialSupply) ERC20("MyToken", "MTK") {
        _mint(msg.sender, initialSupply * 10 ** decimals());
    }
}

Key Takeaways

  • Default decimals() is 18: 1 token = 1018 base units.
  • approve + transferFrom let a contract spend on your behalf.
  • _mint is internal; you decide who may call it.

Security Note

Unlimited approvals to unknown contracts are a top way users lose funds. Approve only what is needed.

22 Burnable Token

Concept: Token supply adjustments

Burning permanently removes tokens from circulation. ERC20Burnable adds burn() for your own tokens and burnFrom() for allowances.

// SPDX-License-Identifier: MIT
pragma solidity ^0.8.20;

import "@openzeppelin/contracts/token/ERC20/ERC20.sol";
import "@openzeppelin/contracts/token/ERC20/extensions/ERC20Burnable.sol";

contract BurnableToken is ERC20, ERC20Burnable {
    constructor() ERC20("BurnToken", "BURN") {
        _mint(msg.sender, 1_000_000 * 10 ** decimals());
    }
}

Key Takeaways

  • burn(n) destroys n of the caller's tokens.
  • burnFrom(a, n) burns from a using the caller's allowance.
  • totalSupply() shrinks accordingly.

Security Note

Burn is irreversible. UIs should double-check amounts, and contracts should never burn on behalf of users without explicit consent.

23 Mintable Token

Concept: Extending functionality

Minting creates new tokens. Restrict it to the owner and enforce a hard cap so the supply cannot grow without limit.

// SPDX-License-Identifier: MIT
pragma solidity ^0.8.20;

import "@openzeppelin/contracts/token/ERC20/ERC20.sol";
import "@openzeppelin/contracts/access/Ownable.sol";

contract MintableToken is ERC20, Ownable {
    uint256 public constant MAX_SUPPLY = 10_000_000 * 1e18;

    constructor() ERC20("MintToken", "MINT") Ownable(msg.sender) {}

    function mint(address to, uint256 amount) external onlyOwner {
        require(totalSupply() + amount <= MAX_SUPPLY, "cap exceeded");
        _mint(to, amount);
    }
}

Key Takeaways

  • OpenZeppelin v5 Ownable takes the initial owner in its constructor.
  • A constant cap makes the maximum supply publicly verifiable.
  • onlyOwner comes from the Ownable base contract.

Security Note

An owner who can mint freely is a centralisation risk. Users must trust that key; document it or move to a multisig/DAO.

24 Access Roles

Concept: Role-based access control

AccessControl replaces a single owner with named roles. An admin grants MINTER_ROLE and BURNER_ROLE to different accounts, following least privilege.

// SPDX-License-Identifier: MIT
pragma solidity ^0.8.20;

import "@openzeppelin/contracts/token/ERC20/ERC20.sol";
import "@openzeppelin/contracts/access/AccessControl.sol";

contract RoleToken is ERC20, AccessControl {
    bytes32 public constant MINTER_ROLE = keccak256("MINTER_ROLE");
    bytes32 public constant BURNER_ROLE = keccak256("BURNER_ROLE");

    constructor() ERC20("RoleToken", "ROLE") {
        _grantRole(DEFAULT_ADMIN_ROLE, msg.sender);
    }

    function mint(address to, uint256 amt) external onlyRole(MINTER_ROLE) {
        _mint(to, amt);
    }

    function burn(address from, uint256 amt) external onlyRole(BURNER_ROLE) {
        _burn(from, amt);
    }
}

Key Takeaways

  • Roles are bytes32 ids; DEFAULT_ADMIN_ROLE manages the others.
  • Grant with grantRole(role, account), revoke with revokeRole.
  • Multiple accounts can hold one role.

Security Note

A burner who can burn anyone's tokens is powerful. Grant roles to contracts or multisigs, never to a hot wallet you do not control.

25 Time-Locked Wallet

Concept: Timelock mechanism

Funds can be deposited any time but only withdrawn after unlockTime. It is a building block for vesting and savings vaults.

// SPDX-License-Identifier: MIT
pragma solidity ^0.8.19;

contract TimeLockedWallet {
    struct Lock {
        uint256 amount;
        uint256 unlockTime;
        bool released;
    }
    
    mapping(address => Lock[]) public locks;
    address public owner;
    
    event Locked(address indexed user, uint256 amount, uint256 unlockTime);
    event Released(address indexed user, uint256 amount);
    
    constructor() {
        owner = msg.sender;
    }
    
    function lock(uint256 _durationDays) public payable {
        require(msg.value > 0, "Must send ether");
        uint256 unlockTime = block.timestamp + (_durationDays * 1 days);
        
        locks[msg.sender].push(Lock({
            amount: msg.value,
            unlockTime: unlockTime,
            released: false
        }));
        
        emit Locked(msg.sender, msg.value, unlockTime);
    }
    
    function release(uint256 _lockIndex) public {
        Lock storage lockItem = locks[msg.sender][_lockIndex];
        require(!lockItem.released, "Already released");
        require(block.timestamp >= lockItem.unlockTime, "Not yet unlocked");
        
        uint256 amount = lockItem.amount;
        lockItem.released = true;
        
        (bool sent, ) = payable(msg.sender).call{value: amount}("");
        require(sent, "Transfer failed");
        
        emit Released(msg.sender, amount);
    }
    
    function releaseAll() public {
        uint256 totalReleased;
        for (uint256 i = 0; i < locks[msg.sender].length; i++) {
            Lock storage lockItem = locks[msg.sender][i];
            if (!lockItem.released && block.timestamp >= lockItem.unlockTime) {
                uint256 amount = lockItem.amount;
                lockItem.released = true;
                totalReleased += amount;
                emit Released(msg.sender, amount);
            }
        }
        if (totalReleased > 0) {
            (bool sent, ) = payable(msg.sender).call{value: totalReleased}("");
            require(sent, "Transfer failed");
        }
    }
    
    function getLockInfo(address _user, uint256 _index) 
        public view returns (
            uint256 amount,
            uint256 unlockTime,
            bool released,
            uint256 timeRemaining
        ) 
    {
        Lock memory lockItem = locks[_user][_index];
        timeRemaining = block.timestamp >= lockItem.unlockTime ? 
            0 : lockItem.unlockTime - block.timestamp;
        return (lockItem.amount, lockItem.unlockTime, lockItem.released, timeRemaining);
    }
    
    function getTotalLocked(address _user) public view returns (uint256) {
        uint256 total;
        for (uint256 i = 0; i < locks[_user].length; i++) {
            if (!locks[_user][i].released) {
                total += locks[_user][i].amount;
            }
        }
        return total;
    }
    
    modifier onlyOwner() {
        require(msg.sender == owner, "Not owner");
        _;
    }
}

Key Takeaways

  • Funds remain inaccessible until unlock time
  • Multiple lock periods possible per user
  • User-controlled release (after time)
  • Useful for vesting schedules

Security Note

If the owner key is lost, funds are stuck forever after the lock. Design recovery deliberately or accept the trade-off.

26 Crowdfunding Contract

Concept: Funding logic and state machines

Backers send ETH until the deadline. If the goal is met the creator withdraws; otherwise each backer can reclaim their own contribution.

// SPDX-License-Identifier: MIT
pragma solidity ^0.8.19;

contract Crowdfunding {
    struct Campaign {
        address creator;
        uint256 goal;
        uint256 raised;
        uint256 deadline;
        bool funded;
        bool claimed;
        bool refunded;
    }
    
    Campaign[] public campaigns;
    mapping(uint256 => mapping(address => uint256)) public contributions;
    
    event CampaignCreated(uint256 indexed id, address creator, uint256 goal);
    event Contributed(uint256 indexed campaignId, address contributor, uint256 amount);
    event CampaignFunded(uint256 indexed campaignId, uint256 raised);
    event FundsClaimed(uint256 indexed campaignId, address recipient);
    event Refunded(uint256 indexed campaignId, address contributor, uint256 amount);
    
    function createCampaign(uint256 _goal, uint256 _durationDays) public returns (uint256) {
        require(_goal > 0, "Goal must be positive");
        require(_durationDays > 0 && _durationDays <= 180, "Duration invalid");
        
        campaigns.push(Campaign({
            creator: msg.sender,
            goal: _goal,
            raised: 0,
            deadline: block.timestamp + (_durationDays * 1 days),
            funded: false,
            claimed: false,
            refunded: false
        }));
        
        emit CampaignCreated(campaigns.length - 1, msg.sender, _goal);
        return campaigns.length - 1;
    }
    
    function contribute(uint256 _campaignId) public payable {
        require(msg.value > 0, "Must contribute");
        Campaign storage campaign = campaigns[_campaignId];
        require(block.timestamp < campaign.deadline, "Campaign ended");
        
        campaign.raised += msg.value;
        contributions[_campaignId][msg.sender] += msg.value;
        
        emit Contributed(_campaignId, msg.sender, msg.value);
        
        if (campaign.raised >= campaign.goal && !campaign.funded) {
            campaign.funded = true;
            emit CampaignFunded(_campaignId, campaign.raised);
        }
    }
    
    function claimFunds(uint256 _campaignId) public {
        Campaign storage campaign = campaigns[_campaignId];
        require(msg.sender == campaign.creator, "Not creator");
        require(campaign.funded, "Campaign not funded");
        require(!campaign.claimed, "Already claimed");
        require(block.timestamp > campaign.deadline, "Still collecting");
        
        campaign.claimed = true;
        uint256 amount = campaign.raised;
        
        (bool sent, ) = payable(campaign.creator).call{value: amount}("");
        require(sent, "Transfer failed");
        
        emit FundsClaimed(_campaignId, campaign.creator);
    }
    
    function refund(uint256 _campaignId) public {
        Campaign storage campaign = campaigns[_campaignId];
        require(block.timestamp > campaign.deadline, "Still collecting");
        require(!campaign.refunded, "Already refunded");
        require(!campaign.funded || block.timestamp > campaign.deadline, "Cannot refund if funded");
        require(contributions[_campaignId][msg.sender] > 0, "No contribution");
        
        uint256 amount = contributions[_campaignId][msg.sender];
        contributions[_campaignId][msg.sender] = 0;
        
        campaign.refunded = true;
        
        (bool sent, ) = payable(msg.sender).call{value: amount}("");
        require(sent, "Transfer failed");
        
        emit Refunded(_campaignId, msg.sender, amount);
    }
    
    function getCampaign(uint256 _id) public view returns (
        address creator,
        uint256 goal,
        uint256 raised,
        uint256 deadline,
        bool funded,
        uint256 remainingTime
    ) {
        Campaign memory c = campaigns[_id];
        return (
            c.creator,
            c.goal,
            c.raised,
            c.deadline,
            c.funded,
            block.timestamp >= c.deadline ? 0 : c.deadline - block.timestamp
        );
    }
    
    function progressPercentage(uint256 _campaignId) public view returns (uint256) {
        Campaign memory c = campaigns[_campaignId];
        return (c.raised * 100) / c.goal;
    }
}

Key Takeaways

  • All-or-nothing funding model
  • Deadline-based refunds for unsuccessful campaigns
  • Creator claims funds only if goal reached
  • Individual contribution tracking

Security Note

Zero the contribution before sending ETH in refund(); otherwise a malicious backer can re-enter and drain the pool.

28 NFT (ERC721)

Concept: ERC721 token standard

ERC721 tokens are unique: every id has exactly one owner. OpenZeppelin provides ownership tracking, approvals and transfers; you add a minting rule.

// SPDX-License-Identifier: MIT
pragma solidity ^0.8.19;

contract SimpleNFT {
    string private _name;
    string private _symbol;
    uint256 private _tokenIdCounter;
    
    mapping(uint256 => address) private _owners;
    mapping(address => uint256) private _balances;
    mapping(uint256 => address) private _tokenApprovals;
    mapping(address => mapping(address => bool)) private _operatorApprovals;
    
    event Transfer(address indexed from, address indexed to, uint256 indexed tokenId);
    event Approval(address indexed owner, address indexed approved, uint256 indexed tokenId);
    event ApprovalForAll(address indexed owner, address indexed operator, bool approved);
    
    constructor(string memory name_, string memory symbol_) {
        _name = name_;
        _symbol = symbol_;
    }
    
    function name() public view virtual returns (string memory) {
        return _name;
    }
    
    function symbol() public view virtual returns (string memory) {
        return _symbol;
    }
    
    function ownerOf(uint256 _tokenId) public view virtual returns (address) {
        address owner = _owners[_tokenId];
        require(owner != address(0), "Token does not exist");
        return owner;
    }
    
    function balanceOf(address _owner) public view virtual returns (uint256) {
        require(_owner != address(0), "Zero address");
        return _balances[_owner];
    }
    
    function mint(address _to) public returns (uint256) {
        uint256 newTokenId = _tokenIdCounter++;
        _safeMint(_to, newTokenId);
        return newTokenId;
    }
    
    function _safeMint(address to, uint256 tokenId) internal virtual {
        require(to != address(0), "Invalid recipient");
        require(_owners[tokenId] == address(0), "Token already minted");
        
        _balances[to] += 1;
        _owners[tokenId] = to;
        
        emit Transfer(address(0), to, tokenId);
    }
    
    function approve(address _approved, uint256 _tokenId) public virtual {
        address owner = _owners[_tokenId];
        require(msg.sender == owner || isApprovedForAll(owner, msg.sender), 
                "Not authorized");
        
        _tokenApprovals[_tokenId] = _approved;
        emit Approval(owner, _approved, _tokenId);
    }
    
    function getApproved(uint256 _tokenId) public view virtual returns (address) {
        require(_owners[_tokenId] != address(0), "Token does not exist");
        return _tokenApprovals[_tokenId];
    }
    
    function setApprovalForAll(address _operator, bool _approved) public virtual {
        _operatorApprovals[msg.sender][_operator] = _approved;
        emit ApprovalForAll(msg.sender, _operator, _approved);
    }
    
    function isApprovedForAll(address _owner, address _operator) public view virtual returns (bool) {
        return _operatorApprovals[_owner][_operator];
    }
    
    function transferFrom(
        address _from,
        address _to,
        uint256 _tokenId
    ) public virtual {
        require(_owns(_from, _tokenId), "Not owner");
        require(_to != address(0), "Invalid recipient");
        
        _approveOrTransfer(msg.sender, _from, _to, _tokenId);
        emit Transfer(_from, _to, _tokenId);
    }
    
    function safeTransferFrom(
        address _from,
        address _to,
        uint256 _tokenId
    ) public virtual {
        transferFrom(_from, _to, _tokenId);
        require(_checkOnERC721Received(_from, _to, _tokenId, ""), 
                "Receiver rejected");
    }
    
    function _approveOrTransfer(
        address spender,
        address from,
        address to,
        uint256 tokenId
    ) internal {
        address approved = getApproved(tokenId);
        
        if (approved != address(0) && approved != spender) {
            delete _tokenApprovals[tokenId];
        }
        _balances[from] -= 1;
        _balances[to] += 1;
        _owners[tokenId] = to;
    }
    
    function _owns(address _owner, uint256 _tokenId) internal view returns (bool) {
        return _owners[_tokenId] == _owner;
    }
    
    function _checkOnERC721Received(
        address from,
        address to,
        uint256 tokenId,
        bytes memory data
    ) internal view returns (bool) {
        if (to.code.length > 0) {
            try IERC721Receiver(to).onERC721Received(msg.sender, from, tokenId, data) 
                returns (bytes4 retval) 
            {
                return retval == IERC721Receiver.onERC721Received.selector;
            } catch {
                return false;
            }
        } else {
            return true;
        }
    }
    
    function _exists(uint256 tokenId) internal view returns (bool) {
        return _owners[tokenId] != address(0);
    }
}

    function onERC721Received(
        address operator,
        address from,
        uint256 tokenId,
        bytes calldata data
    ) external returns (bytes4);
}

Key Takeaways

  • Unique, non-fungible tokens
  • Owner and approval tracking
  • Safe transfer checks for contracts
  • Basis for digital collectibles

Security Note

_safeMint calls back into the recipient (onERC721Received), which is a re-entrancy entry point. Finish state changes before minting.

abstract contract TransparentUpgradeableProxy {

31 Staking Contract

Concept: Stake and rewards

Users lock tokens and earn a time-based reward. Pending rewards are settled every time the position changes, so no loops over users are needed.

contract Staking {
    mapping(address => uint256) public stakes;
    mapping(address => uint256) public rewardDebt;
    mapping(address => uint256) public lastDepositTime;
    
    uint256 public totalStaked;
    uint256 public rewardRate = 1e18; // 1 token per second
    uint256 public startTime;
    
    event Staked(address indexed user, uint256 amount);
    event RewardsClaimed(address indexed user, uint256 amount);
    event Withdrawn(address indexed user, uint256 amount);
    
    constructor() {
        startTime = block.timestamp;
    }
    
    function stake(uint256 _amount) public {
        require(_amount > 0, "Amount must be positive");
        
        updateRewards(msg.sender);
        
        stakes[msg.sender] += _amount;
        totalStaked += _amount;
        lastDepositTime[msg.sender] = block.timestamp;
        
        emit Staked(msg.sender, _amount);
    }
    
    function updateRewards(address _user) public {
        if (stakes[_user] == 0) return;
        
        uint256 timeElapsed = block.timestamp - lastDepositTime[_user];
        uint256 earned = (stakes[_user] * rewardRate * timeElapsed) / 10000;
        
        rewardDebt[_user] += earned;
        lastDepositTime[_user] = block.timestamp;
    }
    
    function claimRewards() public returns (uint256) {
        updateRewards(msg.sender);
        uint256 rewards = rewardDebt[msg.sender];
        
        require(rewards > 0, "No rewards");
        
        rewardDebt[msg.sender] = 0;
        
        (bool sent, ) = payable(msg.sender).call{value: rewards}("");
        require(sent, "Transfer failed");
        
        emit RewardsClaimed(msg.sender, rewards);
        return rewards;
    }
    
    function withdraw(uint256 _amount) public {
        require(stakes[msg.sender] >= _amount, "Insufficient stake");
        
        claimRewards();
        
        stakes[msg.sender] -= _amount;
        totalStaked -= _amount;
        
        (bool sent, ) = payable(msg.sender).call{value: _amount}("");
        require(sent, "Transfer failed");
        
        emit Withdrawn(msg.sender, _amount);
    }
    
    function getEarned(address _user) public view returns (uint256) {
        if (stakes[_user] == 0) return 0;
        uint256 timeElapsed = block.timestamp - lastDepositTime[_user];
        return rewardDebt[_user] + 
               (stakes[_user] * rewardRate * timeElapsed) / 10000;
    }
}

Key Takeaways

  • Accrues rewards over time
  • Time-based reward calculation
  • Can claim while keeping stake
  • Base for DeFi staking protocols

Security Note

If the pool cannot cover rewards, claim() reverts for everyone. Track liabilities and never let rewards eat principal.

32 Reentrancy Protection

Concept: Vulnerability prevention

Reentrancy happens when a contract sends ETH before updating its books; the recipient's code can call back in while the old balance is still recorded. Below: the vulnerable ordering and two fixes.

contract SecureVault {
    mapping(address => uint256) public balances;
    
    // ✅ GOOD: Checks-Effects-Interactions pattern
    function withdrawCEI() public {
        uint256 balance = balances[msg.sender];
        require(balance > 0, "No funds");
        
        balances[msg.sender] = 0; // Effect first
        
        (bool sent, ) = payable(msg.sender).call{value: balance}(""); // Interaction last
        require(sent, "Transfer failed");
    }
    
    // ❌ BAD: Vulnerable to reentrancy
    /*
    function withdrawBad() public {
        (bool sent, ) = payable(msg.sender).call{value: balances[msg.sender]}("");
        require(sent, "");
        balances[msg.sender] = 0; // Too late! Attacker can re-enter
    }
    */
    
    // ✅ Alternative: ReentrancyGuard pattern
    bool private locked;
    
    modifier nonReentrant() {
        require(!locked, "Reentrancy detected");
        locked = true;
        _;
        locked = false;
    }
    
    function withdrawProtected() public nonReentrant {
        uint256 balance = balances[msg.sender];
        require(balance > 0, "No funds");
        
        balances[msg.sender] = 0;
        
        (bool sent, ) = payable(msg.sender).call{value: balance}("");
        require(sent, "Transfer failed");
    }
    
    function deposit() public payable {
        balances[msg.sender] += msg.value;
    }
}

Key Takeaways

  • Update state BEFORE external calls
  • Use OpenZeppelin's ReentrancyGuard
  • Checks-Effects-Interactions pattern is crucial
  • Reentrancy caused major exploits (DAO hack)

Security Note

Cross-function and read-only reentrancy exist too: any external call is an untrusted hand-off. This pattern sits behind the 2016 DAO hack.

33 Ownership Transfer

Concept: Ownable pattern

Handing ownership to a wrong address is irreversible. A two-step transfer makes the new owner explicitly accept, proving the address is live and correct.

// SPDX-License-Identifier: MIT
pragma solidity ^0.8.20;

contract TwoStepOwnable {
    address public owner;
    address public pendingOwner;

    event OwnershipTransferStarted(address indexed from, address indexed to);
    event OwnershipTransferred(address indexed from, address indexed to);

    constructor() { owner = msg.sender; }

    modifier onlyOwner() { require(msg.sender == owner, "not owner"); _; }

    function transferOwnership(address newOwner) external onlyOwner {
        pendingOwner = newOwner;
        emit OwnershipTransferStarted(owner, newOwner);
    }

    function acceptOwnership() external {
        require(msg.sender == pendingOwner, "not pending owner");
        emit OwnershipTransferred(owner, msg.sender);
        owner = msg.sender;
        pendingOwner = address(0);
    }
}

Key Takeaways

  • OpenZeppelin ships this as Ownable2Step.
  • Setting pendingOwner to zero cancels a transfer.
  • Emit events so monitors can alert on ownership changes.

Security Note

Renouncing ownership (owner = 0) permanently disables every onlyOwner function. Make sure that is really intended.

34 Multisig Wallet

Concept: Consensus mechanisms

A multisig needs M of N owners to approve a transaction. One owner submits, others confirm, and once enough confirmations exist anyone among the owners can execute.

contract MultisigWallet {
    struct Transaction {
        address destination;
        uint256 value;
        bytes data;
        bool executed;

    }
    
    mapping(address => bool) public owners;
    mapping(uint256 => mapping(address => bool)) public confirmations;
    Transaction[] public transactions;
    uint256 public required;
    uint256 public transactionCount;
    
    event Submission(uint256 indexed txIndex);

    event Execution(uint256 indexed txIndex);
    
    constructor(address[] memory _owners, uint256 _required) {
        for (uint256 i = 0; i < _owners.length; i++) {
            owners[_owners[i]] = true;
        }

    }

    }

35 Token Vesting

Concept: Vesting and cliffs

Tokens unlock gradually. Nothing is claimable before the cliff; afterwards the vested share grows linearly until the full duration has passed.

contract TokenVesting {
    struct VestingSchedule {
        address beneficiary;
        uint256 cliff;
        uint256 start;
        uint256 duration;
        uint256 totalAmount;
        uint256 released;
        bool revocable;
    }
    
    ERC20Token public token;
    address public owner;
    VestingSchedule[] public vestingSchedules;
    
    event Released(address indexed beneficiary, uint256 amount);
    event Revoked(address indexed beneficiary, uint256 amount);
    
    constructor(address _tokenAddress) {
        token = ERC20Token(_tokenAddress);
        owner = msg.sender;
    }
    
    function createVesting(
        address _beneficiary,
        uint256 _cliff,
        uint256 _duration,
        uint256 _amount,
        bool _revocable
    ) public onlyOwner {
        require(_cliff >= block.timestamp, "Cliff in past");
        require(_duration > _cliff, "Invalid duration");
        
        uint256 vestingStart = _cliff;
        uint256 vestingEnd = _cliff + _duration;
        
        token.transferFrom(msg.sender, address(this), _amount);
        
        vestingSchedules.push(VestingSchedule({
            beneficiary: _beneficiary,
            cliff: _cliff,
            start: vestingStart,
            duration: _duration,
            totalAmount: _amount,
            released: 0,
            revocable: _revocable
        }));
    }
    
    function vestedAmount(uint256 _scheduleId) public view returns (uint256) {
        VestingSchedule memory schedule = vestingSchedules[_scheduleId];
        
        if (block.timestamp < schedule.start) return 0;
        if (block.timestamp >= schedule.start + schedule.duration) {
            return schedule.totalAmount;
        }
        
        uint256 elapsed = block.timestamp - schedule.start;
        return (schedule.totalAmount * elapsed) / schedule.duration;
    }
    
    function releasable(uint256 _scheduleId) public view returns (uint256) {
        VestingSchedule storage schedule = vestingSchedules[_scheduleId];
        uint256 vested = vestedAmount(_scheduleId);
        return vested - schedule.released;
    }
    
    function release(uint256 _scheduleId) public {
        VestingSchedule storage schedule = vestingSchedules[_scheduleId];
        require(msg.sender == schedule.beneficiary, "Not beneficiary");
        
        uint256 amount = releasable(_scheduleId);
        require(amount > 0, "Nothing to release");
        
        schedule.released += amount;
        token.transfer(schedule.beneficiary, amount);
        
        emit Released(schedule.beneficiary, amount);
    }
    
    function revoke(uint256 _scheduleId) public {
        VestingSchedule storage schedule = vestingSchedules[_scheduleId];
        require(msg.sender == owner, "Not owner");
        require(schedule.revocable, "Not revocable");
        
        uint256 unreleased = schedule.totalAmount - schedule.released;
        schedule.totalAmount = schedule.released;
        
        token.transfer(owner, unreleased);
        emit Revoked(schedule.beneficiary, unreleased);
    }
    
    modifier onlyOwner() {
        require(msg.sender == owner, "Not owner");
        _;
    }
}

Key Takeaways

  • Gradual token release over time
  • Cliff period before any release
  • Common for employee compensation
  • Linear vesting schedule

Security Note

Revocable vesting needs an owner with clawback rights: document it clearly. Non-revocable is safer for the beneficiary.

36 DAO Contract

Concept: DAOs and proposals

Token holders create proposals, vote for or against, and after the deadline a passing proposal executes an on-chain call. Quorum prevents a handful of votes from deciding everything.

            joined: true
        });
    }

        require(_votingPower >= minVotingPower, "Insufficient power");
        members[_member] = Member({votingPower: _votingPower, joined: true});
        emit MemberAdded(_member, _votingPower);
    }

        require(members[msg.sender].joined, "Not a member");
        require(bytes(_description).length > 0, "Empty description");
        
        proposals.push(Proposal({
            description: _description,
            proposer: msg.sender,
            forVotes: 0,
            againstVotes: 0,
            startTime: block.timestamp,
            endTime: block.timestamp + votingDuration,
            executed: false,
            passed: false
        }));
        
        uint256 proposalId = proposals.length - 1;
        emit ProposalCreated(proposalId, msg.sender);
        return proposalId;
    }
    
    function vote(uint256 _proposalId, bool _support) public {
        Proposal storage proposal = proposals[_proposalId];
        Member storage voter = members[msg.sender];
        
        require(voter.joined, "Not a member");
        require(!hasVoted[_proposalId][msg.sender], "Already voted");
        require(block.timestamp <= proposal.endTime, "Voting ended");
        
        hasVoted[_proposalId][msg.sender] = true;
        
        if (_support) {
            proposal.forVotes += voter.votingPower;
        } else {
            proposal.againstVotes += voter.votingPower;
        }
        
        emit Voted(_proposalId, msg.sender, _support);
    }
    
    function executeProposal(uint256 _proposalId) public {
        Proposal storage proposal = proposals[_proposalId];
        
        require(block.timestamp > proposal.endTime, "Still voting");
        require(!proposal.executed, "Already executed");
        
        uint256 totalVotes = proposal.forVotes + proposal.againstVotes;
        uint256 totalMembers = getTotalVotingPower();
        
        uint256 quorumReached = (totalVotes * 100) / totalMembers;
        bool passed = proposal.forVotes > proposal.againstVotes;
        bool meetsQuorum = quorumReached >= proposalQuorum;
        
        require(passed && meetsQuorum, "Proposal failed");
        
        proposal.passed = true;
        proposal.executed = true;
        
        emit ProposalExecuted(_proposalId);
    }
    
    function getTotalVotingPower() public view returns (uint256) {
        uint256 total;
        for (address account = address(1); account != address(0); ) {
            if (members[account].joined) {
                total += members[account].votingPower;
            }
            unchecked { account = address(int256(uint256(account)) + 1); }
        }
        return total;
    }
    
    function getProposal(uint256 _id) public view returns (
        uint256 forVotes,
        uint256 againstVotes,
        bool passed,
        uint256 timeRemaining
    ) {
        Proposal memory p = proposals[_id];
        return (
            p.forVotes,
            p.againstVotes,
            p.passed,
            block.timestamp >= p.endTime ? 0 : p.endTime - block.timestamp
        );
    }
    
    modifier onlyOwner() {
        require(msg.sender == owner, "Not owner");
        _;
    }
}

Key Takeaways

  • On-chain governance system
  • Voting power based on membership
  • Quorum requirements for validity
  • Foundation for decentralized organizations

Security Note

Using live balances allows flash-loan voting: borrow tokens, vote, repay. Real DAOs use snapshot balances (ERC20Votes) taken before the proposal.

38 Yield Farming

Concept: Pool distribution logic

Rewards are distributed proportionally to each farmer's share. The trick is a global accumulator (accRewardPerShare) and per-user rewardDebt so that nothing loops over users.

interface IERC20 {
    function transferFrom(address, address, uint256) external returns (bool);
    function transfer(address, uint256) external returns (bool);
    function balanceOf(address) external view returns (uint256);
}

contract YieldFarm {
    IERC20 public lpToken; // Liquidity provider token
    IERC20 public rewardToken;
    
    mapping(address => uint256) public userInfo; // Amount staked
    mapping(address => uint256) public rewardPerTokenPaid;
    mapping(address => uint256) public rewards;
    
    uint256 public totalSupply;
    uint256 public rewardRate = 1e18; // Per second
    uint256 public lastUpdateTime;
    uint256 public rewardPerTokenStored;
    
    event Staked(address indexed user, uint256 amount);
    event Withdrawn(address indexed user, uint256 amount);
    event RewardPaid(address indexed user, uint256 reward);
    
    constructor(address _lpToken, address _rewardToken) {
        lpToken = IERC20(_lpToken);
        rewardToken = IERC20(_rewardToken);
    }
    
    function rewardPerToken() public view returns (uint256) {
        if (totalSupply == 0) {
            return rewardPerTokenStored;
        }
        return rewardPerTokenStored + 
            ((block.timestamp - lastUpdateTime) * rewardRate * 1e18) / totalSupply;
    }
    
    function earned(address _account) public view returns (uint256) {
        return (userInfo[_account] * (rewardPerToken() - rewardPerTokenPaid[_account])) / 1e18 +
            rewards[_account];
    }
    
    function stake(uint256 _amount) public {
        require(_amount > 0, "Amount must be positive");
        
        updateReward(msg.sender);
        
        userInfo[msg.sender] += _amount;
        totalSupply += _amount;
        
        lpToken.transferFrom(msg.sender, address(this), _amount);
        
        emit Staked(msg.sender, _amount);
    }
    
    function withdraw(uint256 _amount) public {
        require(_amount > 0, "Amount must be positive");
        require(userInfo[msg.sender] >= _amount, "Insufficient stake");
        
        updateReward(msg.sender);
        
        userInfo[msg.sender] -= _amount;
        totalSupply -= _amount;
        
        lpToken.transfer(msg.sender, _amount);
        
        emit Withdrawn(msg.sender, _amount);
    }
    
    function claimReward() public returns (uint256) {
        updateReward(msg.sender);
        uint256 reward = rewards[msg.sender];
        
        if (reward > 0) {
            rewards[msg.sender] = 0;
            rewardToken.transfer(msg.sender, reward);
            emit RewardPaid(msg.sender, reward);
        }
        
        return reward;
    }
    
    function updateReward(address _account) public {
        rewardPerTokenStored = rewardPerToken();
        lastUpdateTime = block.timestamp;
        
        if (_account != address(0)) {
            rewards[_account] = earned(_account);
            rewardPerTokenPaid[_account] = rewardPerTokenStored;
        }
    }
    
    function getAllowed() public view returns (IERC20, IERC20) {
        return (lpToken, rewardToken);
    }
}

Key Takeaways

  • Stake LP tokens for rewards
  • Continuous reward accrual
  • Reward rate per second calculation
  • Core mechanism for DeFi farms

Security Note

Fee-on-transfer or rebasing stake tokens break the accounting. Whitelist token types and fund the reward pool for the whole schedule.

39 Escrow Contract

Concept: Escrow logic

A buyer locks ETH for a seller. A neutral arbiter (or the buyer) releases funds when the deal is done, or refunds if it fails. The enum guarantees each escrow ends exactly once.

contract Escrow {
    enum State { Created, Deposited, Released, Disputed, Resolved }
    
    struct Deal {
        address buyer;
        address seller;
        address arbiter;
        uint256 amount;
        State state;
    }
    
    Deal[] public deals;
    
    event DealCreated(uint256 indexed dealId, address indexed buyer, address indexed seller);
    event FundsDeposited(uint256 indexed dealId);
    event FundsReleased(uint256 indexed dealId, address to);
    event DisputeRaised(uint256 indexed dealId);
    event DisputeResolved(uint256 indexed dealId, address to);
    
    function createDeal(address _seller, address _arbiter) public payable returns (uint256) {
        require(msg.value > 0, "Must send funds");
        require(_seller != msg.sender, "Buyer and seller same");
        require(_arbiter != msg.sender, "Arbiter cannot be buyer");
        require(_arbiter != _seller, "Arbiter cannot be seller");
        
        deals.push(Deal({
            buyer: msg.sender,
            seller: _seller,
            arbiter: _arbiter,
            amount: msg.value,
            state: State.Created
        }));
        
        uint256 dealId = deals.length - 1;
        emit DealCreated(dealId, msg.sender, _seller);
        return dealId;
    }
    
    function confirmDeposit(uint256 _dealId) public {
        Deal storage deal = deals[_dealId];
        require(msg.sender == deal.buyer, "Not buyer");
        require(deal.state == State.Created, "Wrong state");
        
        deal.state = State.Deposited;
        emit FundsDeposited(_dealId);
    }
    
    function release(uint256 _dealId) public {
        Deal storage deal = deals[_dealId];
        require(msg.sender == deal.seller, "Not seller");
        require(deal.state == State.Deposited, "Wrong state");
        
        deal.state = State.Released;
        (bool sent, ) = payable(deal.seller).call{value: deal.amount}("");
        require(sent, "Release failed");
        
        emit FundsReleased(_dealId, deal.seller);
    }
    
    function raiseDispute(uint256 _dealId) public {
        Deal storage deal = deals[_dealId];
        require(
            msg.sender == deal.buyer || msg.sender == deal.seller,
            "Not party"
        );
        require(deal.state == State.Deposited, "Wrong state");
        
        deal.state = State.Disputed;
        emit DisputeRaised(_dealId);
    }
    
    function resolveDispute(uint256 _dealId, address _to) public {
        Deal storage deal = deals[_dealId];
        require(msg.sender == deal.arbiter, "Not arbiter");
        require(deal.state == State.Disputed, "Not disputed");
        
        deal.state = State.Resolved;
        (bool sent, ) = payable(_to).call{value: deal.amount}("");
        require(sent, "Resolution failed");
        
        emit DisputeResolved(_dealId, _to);
    }
    
    function refund(uint256 _dealId) public {
        Deal storage deal = deals[_dealId];
        require(msg.sender == deal.arbiter, "Not arbiter");
        require(deal.state == State.Disputed, "Not disputed");
        
        deal.state = State.Resolved;
        (bool sent, ) = payable(deal.buyer).call{value: deal.amount}("");
        require(sent, "Refund failed");
        
        emit DisputeResolved(_dealId, deal.buyer);
    }
    
    function getDeal(uint256 _id) 
        public view returns (
            address buyer,
            address seller,
            address arbiter,
            uint256 amount,
            uint8 state,
            uint256 index
        ) 
    {
        Deal memory d = deals[_id];
        return (d.buyer, d.seller, d.arbiter, d.amount, uint8(d.state), _id);
    }
}

Key Takeaways

  • Third-party arbitration system
  • Safe peer-to-peer transactions
  • Dispute resolution mechanism
  • Trustless escrow service

41 Gas Refunds

Concept: Refund mechanics

A contract can reimburse trusted keepers for the gas they spend. Measure gasleft() before and after, add a fixed overhead, cap the gas price and pay the caller from a funded pool.

// SPDX-License-Identifier: MIT
pragma solidity ^0.8.20;

contract GasRefund {
    address public owner = msg.sender;
    mapping(address => bool) public keepers;
    uint256 public constant OVERHEAD = 30_000;      // gas outside the measured part
    uint256 public constant MAX_GAS_PRICE = 100 gwei;
    uint256 public counter;

    modifier onlyOwner() { require(msg.sender == owner, "not owner"); _; }

    receive() external payable {}                    // fund the refund pool

    function setKeeper(address k, bool ok) external onlyOwner { keepers[k] = ok; }

    function performTask() external {
        require(keepers[msg.sender], "not a keeper");
        uint256 startGas = gasleft();

        counter++;                                   // the actual work

        uint256 price = tx.gasprice < MAX_GAS_PRICE ? tx.gasprice : MAX_GAS_PRICE;
        uint256 refund = (startGas - gasleft() + OVERHEAD) * price;
        if (refund > address(this).balance) refund = address(this).balance;
        (bool ok, ) = msg.sender.call{value: refund}("");
        require(ok, "refund failed");
    }
}

Key Takeaways

  • tx.gasprice is what the sender chose to pay per gas.
  • Capping the price stops keepers from over-billing the pool.
  • OVERHEAD approximates the intrinsic cost you cannot measure.

Security Note

Without the keeper whitelist and cap, anyone can farm the pool by calling with a huge gas price. Never refund unauthenticated callers.

42 Governance Contract

Concept: On-chain governance

Members vote to change a protocol parameter (the fee). Passing proposals wait in a timelock queue before taking effect, giving users time to react or exit.

// SPDX-License-Identifier: MIT
pragma solidity ^0.8.20;

contract FeeGovernance {
    uint256 public feeBps = 30;
    uint256 public constant MAX_FEE_BPS = 1_000;
    uint256 public constant VOTING_PERIOD = 3 days;
    uint256 public constant TIMELOCK = 2 days;
    uint256 public immutable memberCount;
    mapping(address => bool) public isMember;

    struct Proposal { uint256 newFee; uint256 yes; uint256 no;
                      uint256 voteEnd; uint256 eta; bool executed; }
    Proposal[] public proposals;
    mapping(uint256 => mapping(address => bool)) public voted;

    constructor(address[] memory members) {
        for (uint256 i = 0; i < members.length; i++) isMember[members[i]] = true;
        memberCount = members.length;
    }

    modifier onlyMember() { require(isMember[msg.sender], "not member"); _; }

    function propose(uint256 newFee) external onlyMember returns (uint256 id) {
        require(newFee <= MAX_FEE_BPS, "fee too high");
        id = proposals.length;
        proposals.push(Proposal(newFee, 0, 0, block.timestamp + VOTING_PERIOD, 0, false));
    }

    function vote(uint256 id, bool support) external onlyMember {
        Proposal storage p = proposals[id];
        require(block.timestamp < p.voteEnd, "voting closed");
        require(!voted[id][msg.sender], "already voted");
        voted[id][msg.sender] = true;
        if (support) p.yes++; else p.no++;
    }

    function queue(uint256 id) external {
        Proposal storage p = proposals[id];
        require(block.timestamp >= p.voteEnd && p.eta == 0, "cannot queue");
        require(p.yes > p.no && p.yes * 2 > memberCount, "not passed");
        p.eta = block.timestamp + TIMELOCK;
    }

    function execute(uint256 id) external {
        Proposal storage p = proposals[id];
        require(p.eta != 0 && block.timestamp >= p.eta, "timelock active");
        require(!p.executed, "already executed");
        p.executed = true;
        feeBps = p.newFee;
    }
}

Key Takeaways

  • Lifecycle: propose, vote, queue, wait, execute.
  • A hard MAX_FEE_BPS bounds what governance can ever do.
  • Basis points: 100 bps = 1%.

Security Note

Governance is a privileged actor. Bound its powers in code so a captured vote cannot set a 100% fee or drain funds.

43 Dynamic Fees

Concept: Fee adjustment

The fee depends on the payment size: bigger payments get a lower rate. The owner can adjust tiers but never above a hard cap.

// SPDX-License-Identifier: MIT
pragma solidity ^0.8.20;

contract DynamicFees {
    address public owner = msg.sender;
    uint256 public constant MAX_FEE_BPS = 500;       // 5%
    uint256 public smallFeeBps = 100;                // < 1 ETH
    uint256 public mediumFeeBps = 50;                // < 10 ETH
    uint256 public largeFeeBps = 25;                 // >= 10 ETH
    uint256 public feesCollected;

    modifier onlyOwner() { require(msg.sender == owner, "not owner"); _; }

    function feeBpsFor(uint256 amount) public view returns (uint256) {
        if (amount < 1 ether) return smallFeeBps;
        if (amount < 10 ether) return mediumFeeBps;
        return largeFeeBps;
    }

    function setFees(uint256 s, uint256 m, uint256 l) external onlyOwner {
        require(s <= MAX_FEE_BPS && m <= MAX_FEE_BPS && l <= MAX_FEE_BPS, "above cap");
        smallFeeBps = s; mediumFeeBps = m; largeFeeBps = l;
    }

    function pay(address payable to) external payable {
        uint256 fee = msg.value * feeBpsFor(msg.value) / 10_000;
        feesCollected += fee;
        (bool ok, ) = to.call{value: msg.value - fee}("");
        require(ok, "payment failed");
    }

    function withdrawFees() external onlyOwner {
        uint256 amt = feesCollected;
        feesCollected = 0;
        (bool ok, ) = owner.call{value: amt}("");
        require(ok, "withdraw failed");
    }
}

Key Takeaways

  • Divide by 10,000 to convert basis points to a ratio.
  • Rounding down favours the payer by up to 1 wei: acceptable here.
  • Emit an event when fees change so users can track it.

Security Note

Tiered fees can be gamed by splitting payments. Decide whether that is acceptable, and never let an owner raise fees without a cap or delay.

44 Chain Interaction

Concept: Inter-contract calls

Contracts talk to each other through interfaces. Wrapping the call in try/catch lets the caller survive a failure in the other contract instead of reverting.

// SPDX-License-Identifier: MIT
pragma solidity ^0.8.20;

interface ICounter {
    function increment() external;
    function count() external view returns (uint256);
}

contract Counter is ICounter {
    uint256 public override count;

    function increment() external override {
        count += 1;
    }
}

contract Caller {
    ICounter public immutable target;
    uint256 public failures;

    constructor(address counter) {
        target = ICounter(counter);
    }

    function bump() external returns (bool) {
        try target.increment() {
            return true;
        } catch {
            failures++;
            return false;
        }
    }

    function read() external view returns (uint256) {
        return target.count();
    }
}

Key Takeaways

  • An interface lists function signatures only, no logic.
  • try/catch handles reverts of external calls, not internal errors.
  • Deploy Counter first, then pass its address to Caller.

Security Note

Every external call hands control to code you did not write. Treat addresses passed in constructors as trusted only if you verified them.

45 ERC1155 Token

Concept: ERC1155 standard

ERC1155 holds many token types (fungible and non-fungible) in one contract, with batch transfers that save gas. Ideal for game items.

// SPDX-License-Identifier: MIT
pragma solidity ^0.8.20;

import "@openzeppelin/contracts/token/ERC1155/ERC1155.sol";
import "@openzeppelin/contracts/access/Ownable.sol";

contract GameItems is ERC1155, Ownable {
    uint256 public constant GOLD = 1;     // fungible
    uint256 public constant SWORD = 2;    // semi-fungible
    uint256 public constant CROWN = 3;    // unique (supply of 1)

    constructor() ERC1155("ipfs://REPLACE_WITH_CID/{id}.json") Ownable(msg.sender) {
        _mint(msg.sender, GOLD, 1_000_000, "");
        _mint(msg.sender, SWORD, 100, "");
        _mint(msg.sender, CROWN, 1, "");
    }

    function mint(address to, uint256 id, uint256 amount) external onlyOwner {
        _mint(to, id, amount, "");
    }

    function mintBatch(address to, uint256[] calldata ids, uint256[] calldata amounts)
        external onlyOwner
    {
        _mintBatch(to, ids, amounts, "");
    }
}

Key Takeaways

  • Balance lookup is balanceOf(account, id).
  • safeBatchTransferFrom moves many ids in one transaction.
  • The URI contains {id} which clients substitute per token.

Security Note

Like ERC721, safe transfers call the receiver. Update your state before minting or transferring to contracts.

46 NFT Royalty System

Concept: Revenue sharing

EIP-2981 lets an NFT declare a royalty. This example enforces it in its own sale function by splitting the price between the creator and the seller.

// SPDX-License-Identifier: MIT
pragma solidity ^0.8.20;

import "@openzeppelin/contracts/token/ERC721/ERC721.sol";
import "@openzeppelin/contracts/token/common/ERC2981.sol";
import "@openzeppelin/contracts/access/Ownable.sol";

contract RoyaltyNFT is ERC721, ERC2981, Ownable {
    uint256 private _nextId;
    mapping(uint256 => uint256) public price;       // 0 = not for sale

    constructor() ERC721("RoyaltyNFT", "RNFT") Ownable(msg.sender) {
        _setDefaultRoyalty(msg.sender, 500);        // 5% to the creator
    }

    function mint(address to) external onlyOwner returns (uint256 id) {
        id = _nextId++;
        _mint(to, id);
    }

    function list(uint256 id, uint256 _price) external {
        require(ownerOf(id) == msg.sender, "not owner");
        price[id] = _price;
    }

    function buy(uint256 id) external payable {
        uint256 p = price[id];
        address seller = ownerOf(id);
        require(p > 0 && msg.value == p, "bad price");
        (address receiver, uint256 royalty) = royaltyInfo(id, p);
        delete price[id];
        _transfer(seller, msg.sender, id);
        _pay(receiver, royalty);
        _pay(seller, p - royalty);
    }

    function _pay(address to, uint256 amt) private {
        (bool ok, ) = to.call{value: amt}("");
        require(ok, "payment failed");
    }

    function supportsInterface(bytes4 id)
        public view override(ERC721, ERC2981) returns (bool)
    {
        return super.supportsInterface(id);
    }
}

Key Takeaways

  • royaltyInfo(id, price) returns (receiver, amount).
  • Basis points again: 500 = 5%.
  • Both parents define supportsInterface, so you must override it.

Security Note

ERC-2981 is only a hint. Marketplaces may ignore it, so royalties are enforceable only inside sales that go through your own contract.

47 Subscription Contract

Concept: Subscription logic

Blockchains cannot auto-debit, so a keeper (or the merchant) calls charge() when a period is due. The subscriber pre-approves an allowance and can cancel at any time.

// SPDX-License-Identifier: MIT
pragma solidity ^0.8.20;

import "@openzeppelin/contracts/token/ERC20/IERC20.sol";
import "@openzeppelin/contracts/token/ERC20/utils/SafeERC20.sol";

contract Subscription {
    using SafeERC20 for IERC20;

    IERC20 public immutable token;
    address public immutable merchant;
    uint256 public immutable price;
    uint256 public immutable period;

    mapping(address => bool) public active;
    mapping(address => uint256) public nextCharge;

    event Subscribed(address indexed user);
    event Cancelled(address indexed user);
    event Charged(address indexed user, uint256 amount);

    constructor(IERC20 _token, address _merchant, uint256 _price, uint256 _period) {
        token = _token; merchant = _merchant; price = _price; period = _period;
    }

    function subscribe() external {
        require(!active[msg.sender], "already subscribed");
        active[msg.sender] = true;
        emit Subscribed(msg.sender);
        _charge(msg.sender);
    }

    function cancel() external {
        active[msg.sender] = false;
        emit Cancelled(msg.sender);
    }

    function charge(address user) external {
        require(active[user], "not active");
        require(block.timestamp >= nextCharge[user], "not due yet");
        _charge(user);
    }

    function _charge(address user) private {
        nextCharge[user] = block.timestamp + period;
        token.safeTransferFrom(user, merchant, price);
        emit Charged(user, price);
    }
}

Key Takeaways

  • Users control spending through the ERC20 allowance they set.
  • Anyone can trigger charge(), but only when it is due.
  • Cancel takes effect immediately; no refund logic needed.

Security Note

Approve only a few periods' worth of tokens, not unlimited. A compromised merchant contract could otherwise drain the allowance.

48 Flash Loan

Concept: Borrowing and repayment in a single transaction

A flash loan is uncollateralised because it must be repaid inside the same transaction. The pool lends, calls back the borrower, then checks its balance; if it is short, the whole transaction reverts as if nothing happened.

// SPDX-License-Identifier: MIT
pragma solidity ^0.8.20;

import "@openzeppelin/contracts/token/ERC20/IERC20.sol";
import "@openzeppelin/contracts/token/ERC20/utils/SafeERC20.sol";
import "@openzeppelin/contracts/utils/ReentrancyGuard.sol";

interface IFlashBorrower {
    function onFlashLoan(address token, uint256 amount, uint256 fee, bytes calldata data) external;
}

contract FlashLoanPool is ReentrancyGuard {
    using SafeERC20 for IERC20;

    IERC20 public immutable token;
    uint256 public constant FEE_BPS = 9;             // 0.09%

    constructor(IERC20 _token) { token = _token; }

    function flashLoan(address borrower, uint256 amount, bytes calldata data)
        external nonReentrant
    {
        uint256 balanceBefore = token.balanceOf(address(this));
        require(amount <= balanceBefore, "not enough liquidity");
        uint256 fee = amount * FEE_BPS / 10_000;

        token.safeTransfer(borrower, amount);
        IFlashBorrower(borrower).onFlashLoan(address(token), amount, fee, data);

        require(token.balanceOf(address(this)) >= balanceBefore + fee, "loan not repaid");
    }
}

Key Takeaways

  • The borrower repays by transferring tokens back inside onFlashLoan.
  • Atomicity is the collateral: failure reverts the entire transaction.
  • nonReentrant stops nested loans that game the balance check.

Security Note

Flash loans are why weak oracles and instantly-manipulable prices get exploited. Design protocols assuming attackers have unlimited capital for one transaction.

49 Cross-Chain Bridge

Concept: Bridging and interoperability

A lock-and-mint bridge: tokens are locked on the source chain, a relayer reports the event, and a wrapped token is minted on the destination. Burning the wrapped token later unlocks the original. Simplified with a single trusted relayer.

// SPDX-License-Identifier: MIT
pragma solidity ^0.8.20;

import "@openzeppelin/contracts/token/ERC20/ERC20.sol";
import "@openzeppelin/contracts/token/ERC20/IERC20.sol";
import "@openzeppelin/contracts/token/ERC20/utils/SafeERC20.sol";

// ---- Source chain: locks the real token ----
contract BridgeSource {
    using SafeERC20 for IERC20;
    IERC20 public immutable token;
    address public immutable relayer;
    uint256 public nonce;
    mapping(bytes32 => bool) public processed;

    event Locked(address indexed from, address to, uint256 amount, uint256 nonce);

    constructor(IERC20 _token, address _relayer) { token = _token; relayer = _relayer; }

    function lock(address to, uint256 amount) external {
        token.safeTransferFrom(msg.sender, address(this), amount);
        emit Locked(msg.sender, to, amount, nonce++);
    }

    function unlock(address to, uint256 amount, uint256 srcChainId, uint256 destNonce) external {
        require(msg.sender == relayer, "not relayer");
        bytes32 id = keccak256(abi.encode(srcChainId, destNonce));
        require(!processed[id], "already processed");   // replay protection
        processed[id] = true;
        token.safeTransfer(to, amount);
    }
}

// ---- Destination chain: mints a wrapped token ----
contract WrappedToken is ERC20 {
    address public immutable bridge;
    constructor(address _bridge) ERC20("Wrapped MTK", "wMTK") { bridge = _bridge; }
    function mint(address to, uint256 a) external { require(msg.sender == bridge); _mint(to, a); }
    function burn(address from, uint256 a) external { require(msg.sender == bridge); _burn(from, a); }
}

contract BridgeDest {
    WrappedToken public immutable wrapped;
    address public immutable relayer;
    uint256 public nonce;
    mapping(bytes32 => bool) public processed;

    event Burned(address indexed from, address to, uint256 amount, uint256 nonce);

    constructor(address _relayer) { relayer = _relayer; wrapped = new WrappedToken(address(this)); }

    function mintWrapped(address to, uint256 amount, uint256 srcChainId, uint256 srcNonce) external {
        require(msg.sender == relayer, "not relayer");
        bytes32 id = keccak256(abi.encode(srcChainId, srcNonce));
        require(!processed[id], "already processed");
        processed[id] = true;
        wrapped.mint(to, amount);
    }

    function bridgeBack(address to, uint256 amount) external {
        wrapped.burn(msg.sender, amount);
        emit Burned(msg.sender, to, amount, nonce++);
    }
}

Key Takeaways

  • Every cross-chain message needs a unique id and a processed set.
  • Supply invariant: locked on A always equals wrapped minted on B.
  • Trust model = whoever controls the relayer. Real bridges use many validators or light clients.

Security Note

Bridges hold huge pooled funds and are among the most-hacked DeFi components (Ronin, Wormhole, Nomad). Key compromise and message validation are the usual culprits.

50 Deflationary Token

Concept: Supply dynamics

Every transfer burns a percentage, shrinking supply over time. In OpenZeppelin v5 you override the single _update hook that all mints, burns and transfers pass through.

// SPDX-License-Identifier: MIT
pragma solidity ^0.8.20;

import "@openzeppelin/contracts/token/ERC20/ERC20.sol";

contract DeflationaryToken is ERC20 {
    uint256 public constant BURN_BPS = 100;          // 1% per transfer

    constructor() ERC20("DeflaToken", "DEFL") {
        _mint(msg.sender, 1_000_000 * 10 ** decimals());
    }

    function _update(address from, address to, uint256 value) internal override {
        // apply the burn only on real transfers, not on mint or burn
        if (from != address(0) && to != address(0)) {
            uint256 burnAmount = value * BURN_BPS / 10_000;
            if (burnAmount > 0) {
                super._update(from, address(0), burnAmount);
                value -= burnAmount;
            }
        }
        super._update(from, to, value);
    }
}

Key Takeaways

  • from == 0 means mint, to == 0 means burn.
  • The receiver gets value - burn, so transfers are lossy.
  • totalSupply decreases automatically through the burn.

Security Note

Fee-on-transfer behaviour breaks protocols that assume the received amount equals the sent amount (AMMs, vaults, escrows). Test integrations explicitly.
